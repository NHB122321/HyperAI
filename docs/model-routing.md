# Как HyperAI выбирает модель: разбор для Артёма

Теперь перед обращением к OpenAI агент выбирает модель. В режиме `auto` простые сообщения получает `FAST_MODEL`, а запросы с признаками сложной задачи — `SMART_MODEL`. Команды `/fast` и `/smart` закрепляют выбор вручную, `/auto` возвращает автоматический режим. По умолчанию это `gpt-5.6-luna` и `gpt-6-astra`.

Читай код в таком порядке: `config.py` → `model_router.py` → `process_message` в `HyperAI.py` → `telegram_bot.py`. Затем посмотри `logger.py`, `voice_tools.py` и тесты. Так ты увидишь, откуда берутся настройки, как принимается решение и куда оно передаётся.

## 1. Конфигурация: значения отдельно от поведения

Раньше имя текстовой модели задавалось одной константой. Теперь в `config.py` несколько настроек:

```python
FAST_MODEL = _model_setting("FAST_MODEL", "gpt-5.6-luna")
SMART_MODEL = _model_setting("SMART_MODEL", "gpt-6-astra")
TRANSCRIPTION_MODEL = _model_setting("TRANSCRIPTION_MODEL", "gpt-transcribe")
MODEL_MODE = os.getenv("MODEL_MODE", "auto").strip().lower()
```

`os.getenv` читает переменную окружения. Второй аргумент — запасное значение, если переменная отсутствует. Функция `_model_setting` убирает пробелы по краям и запрещает пустое имя модели. Поэтому ошибку вроде `SMART_MODEL=` ты увидишь при запуске, с названием проблемной настройки.

Перед этим `load_dotenv` загружает `.env` из папки, где находится `config.py`. `Path(__file__).resolve().parent` вычисляет именно эту папку, независимо от того, откуда запустили Python. `override=False` сохраняет приоритет переменных, уже заданных в окружении процесса.

Режим проверяется отдельно: разрешены только `auto`, `fast`, `smart`. Вызовы `.strip().lower()` позволяют записать ` SMART ` и получить `smart`. Переменная `MODEL = FAST_MODEL` оставлена для совместимости со старым импортом. `AGENT_INSTRUCTIONS` и `MAX_AGENT_STEPS` сохраняют прежнее содержание.

После изменения `.env` перезапусти бота: эти значения читаются при импорте модулей. Проверка имени означает лишь, что оно непустое; доступность модели для твоего API-ключа выясняется при реальном обращении.

## 2. ModelDecision: оформляем результат выбора

```python
@dataclass(frozen=True)
class ModelDecision:
    """Результат выбора: модель, режим пользователя и объяснение."""

    model: str
    mode: str
    reason: str
```

`dataclass` создаёт удобный объект с перечисленными полями: Python сам добавляет конструктор и сравнение объектов. Аннотация `str` сообщает читателю и редактору, что поле содержит строку. Сама аннотация не проверяет данные при выполнении; проверки написаны отдельными условиями.

`frozen=True` запрещает присваивать полям новые значения после создания. Получив решение, код читает `decision.model` и передаёт его дальше. Поле `mode` хранит выбранный режим: при автоматическом выборе Astra оно всё равно равно `auto`. Поле `reason` объясняет сработавшее правило и помогает проверять поведение в журнале.

## 3. ModelRouter: прозрачные правила сложности

Конструктор `__init__` принимает имена двух моделей и режим по умолчанию. Обычно они приходят из конфигурации; в тестах можно передать `test-fast` и `test-smart`. Сначала конструктор проверяет параметры, затем сохраняет их в `self` — конкретном экземпляре маршрутизатора.

Методы с `@staticmethod` не получают `self`: им достаточно переданного значения. Так устроены `_validate_model` и `_validate_mode`. Методы с `@classmethod` получают `cls`, то есть класс, и через него обращаются к общим правилам. Это используется в `_complexity_reason` и `is_continuation`.

Правила записаны регулярными выражениями — шаблонами поиска текста. Например, `\b` обозначает границу слова, `|` разделяет варианты, а `\w*` разрешает продолжение слова. Префикс `r` перед строкой позволяет удобно записывать обратные косые черты. `re.compile` подготавливает шаблон для повторного использования, `search` ищет совпадение внутри строки, `fullmatch` требует совпадения всей строки.

Сложными считаются запросы на анализ, исследование, сравнение, разработку плана, написание или разбор кода и некоторые задачи из нескольких шагов. Для кода обычно нужны одновременно тема и действие: «Объясни этот код». Само слово Python в вопросе «Что такое Python?» не включает smart. Блок кода в тройных обратных кавычках тоже считается признаком сложности.

Есть дополнительный порог объёма: от 1600 символов или 220 слов. Это помогает с длинными запросами, в которых нет знакомых глаголов. Короткие просьбы показать бюджет, записать расход, назвать цену BTC или сохранить факт остаются быстрыми, пока другое правило не обнаружило сложность.

## 4. choose: порядок принятия решения

Сначала `choose` проверяет, что сообщение — строка, и определяет режим: явно переданный `mode` или настройка по умолчанию. В `fast` сразу возвращается быстрая модель, в `smart` — умная. Содержание запроса не отменяет ручной выбор.

В `auto` сначала оценивается текущий текст. Затем, если самостоятельных признаков сложности нет, проверяется короткое продолжение: «Продолжи», «Подробнее», «А почему?» и несколько английских вариантов. Если оно относится к предыдущей сложной задаче, выбирается smart. В остальных случаях возвращается fast.

Здесь нет дополнительного вызова OpenAI: решение принимает обычный Python. Можно передать одну фразу в `choose`, посмотреть три поля результата и понять, почему выбран именно этот путь.

## 5. Два разных вида контекста

`previous_response_id` связывает очередной запрос с предыдущим ответом через Responses API. Он нужен для продолжения разговора с моделью и передачи результатов инструментов. Сам маршрутизатор этот идентификатор не анализирует.

`previous_user_message` содержит текст последнего самостоятельного запроса. В Telegram он берётся из `chat_messages`. Это опора только для оценки коротких продолжений. После успешной обработки нового самостоятельного запроса опора обновляется; слова «Продолжи» и «Подробнее» её не заменяют.

Поэтому последовательность «Проанализируй расходы» → «Продолжи» → «Подробнее» продолжает выбирать smart. Если следующим сообщением придёт «Какая цена BTC?», выбирается fast и появляется новая опора. Проверка `is_continuation` используется и внутри маршрутизатора, и при обновлении состояния, чтобы оба места одинаково понимали продолжение.

## 6. Один выбор на весь цикл инструментов

В начале `process_message` выполняются выбор и запись причины в журнал:

```python
decision = model_router.choose(
    user_message,
    mode=mode,
    previous_user_message=previous_user_message
)
log_model_route(decision.mode, decision.model, decision.reason)
```

После этого `decision.model` используется и в первом запросе к OpenAI, и во всех запросах с результатами инструментов. Если модель попросила вызвать функцию, Python выполняет её, собирает `function_call_output` и возвращает результат той же выбранной модели. Предел цикла по-прежнему задаёт `MAX_AGENT_STEPS`.

Список инструментов, инструкции и форма результата функции сохранены: вызывающая сторона получает пару `(текст_ответа, идентификатор_ответа)`. Звёздочка в сигнатуре `process_message` означает, что новые параметры после неё передаются по имени: `mode="fast"`, `previous_user_message=...`. Это делает места вызова понятнее.

Автоматического перехода на другую модель после ошибки API здесь нет. Ошибка доходит до обработчика Telegram, который показывает сообщение о сбое. Последний успешно полученный контекст при таком сбое сохраняется.

## 7. Telegram: режим принадлежит чату

Три словаря хранят разные данные по `chat_id`: `chat_contexts` — идентификатор ответа, `chat_modes` — режим, `chat_messages` — опорный запрос. Метод `.get(chat_id, MODEL_MODE)` возвращает настройку по умолчанию, пока режим этого чата не выбран явно.

Общий обработчик `set_model_mode` сначала проверяет доступ, затем сохраняет режим и отправляет подтверждение. `/auto`, `/fast`, `/smart` вызывают его с нужной строкой. `/mode` только показывает состояние. Для этих команд запрос к модели не нужен. Переключение режима сохраняет историю; `/reset` удаляет историю и опорный текст текущего чата, сохраняя выбранный режим.

`process_message` использует синхронный клиент OpenAI. Вызов через `await asyncio.to_thread(...)` переносит эту работу в отдельный поток, позволяя циклу асинхронного приложения продолжать работу во время ожидания. `await` получает результат, когда функция завершится. Сам по себе этот приём не ускоряет ответ модели и не включает параллельную обработку всех сообщений.

Длинный ответ отправляется последовательными частями по 4000 символов. Срез `answer[offset:offset + 4000]` берёт очередной фрагмент. Текст сохраняется целиком, хотя граница может пройти внутри предложения. Пустой текст заменяется понятным служебным ответом.

## 8. Голос, журнал и консоль

В `voice_tools.py` имя модели распознавания теперь берётся из `TRANSCRIPTION_MODEL`. Значение по умолчанию осталось прежним: `gpt-transcribe`. Сначала аудио превращается в текст, затем этот текст проходит через тот же `ask_hyperai` и ModelRouter. Режим smart относится к обработке запроса после распознавания. Само распознавание также запускается через `asyncio.to_thread`.

Функция `log_model_route` добавляет в `agent.log` строку с режимом, именем модели и причиной. Например, при проверке маршрутизации можно сопоставить просьбу про анализ с причиной «Запрошен анализ, исследование или обоснование». Остальные записи о сообщениях, инструментах и результатах остаются.

Консольный `run_agent` теперь вызывает общий `process_message`. Дублирующий цикл работы модели убран, поэтому исправление общего механизма сразу действует в Telegram и консоли. В консоли также работают команды режимов и сохранение опорного запроса.

## 9. Проследи два сообщения

«Я потратил 300 лей на продукты» в `auto` выбирает fast. Дальше модель получает текст и существующие инструменты. Ожидаемый сценарий — вызов `add_expense` с суммой и категорией, запись через финансовый модуль, возврат результата той же модели и подтверждение пользователю. Маршрутизатор выбирает только модель; название инструмента и аргументы определяются последующим ответом модели.

«Проанализируй мои финансы за текущий месяц» выбирает smart по слову «проанализируй». Модель может вызвать `get_financial_insights` и другие доступные финансовые функции, получить фактические данные и подготовить выводы. Все шаги этого запроса используют smart. Последующие «Продолжи» и «Подробнее» сохраняют привязку к анализу. Конкретные вызовы инструментов в живом запросе зависят от ответа API.

## 10. Что доказывают тесты

Тесты конфигурации проверяют значения, переопределения и ошибки. Тесты маршрутизатора проверяют русские и английские фразы, приоритет ручного режима и продолжения. В интеграционных тестах агента ответ OpenAI подменяется заранее заданной последовательностью, а финансовые функции действительно работают с временной SQLite-базой и память — с временным JSON-файлом. Проверяются реальные записи и результаты, передаваемые обратно модели.

Тесты Telegram отдельно подменяют вызовы агента и отправку сообщений, проверяя режимы, доступ, историю, кнопки, голос и длинные ответы. Это проверка нашей логики без внешних запросов. Доступность моделей по твоему ключу, реальная задержка и правильность самостоятельного выбора инструментов моделью этими тестами не измеряются.

Правила могут пропустить сложную формулировку или принять простую за сложную: у них нет полноценного понимания смысла. Ручные режимы позволяют управлять такими случаями. Словари состояния находятся в памяти процесса, поэтому после перезапуска история привязки, опорный запрос и выбранный режим исчезают; снова применяется `MODEL_MODE`.

Для самостоятельной практики попробуй три небольших задания: предсказать модель и причину для пяти своих сообщений; добавить одно правило вместе с примером сложного и похожего простого запроса в тестах; проследить в отладчике, как `call_id` связывает вызов инструмента с возвращённым результатом.
